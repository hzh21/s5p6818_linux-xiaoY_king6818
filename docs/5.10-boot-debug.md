# 5.10 启动失败排查手册（2026-11-20）

## 现象

`next=510` 后板子约 40 秒又回到 4.14，串口（如果有人守）看不到任何内核输出之前
的东西也看不出来 —— 因为内核在 systemd 阶段才崩，而板上没有常驻串口。

## 结论（先看这个）

**`CONFIG_IPV6=m` 会让 5.10 在开机 6 秒时 panic。** 必须 `CONFIG_IPV6=y`。

串口实证：

```

[    5.929460] NET: Registered protocol family 10
[    5.929782] Unable to handle kernel paging request at virtual address ffffffffffffff63
[    5.978436] Internal error: Oops: 0000000096000005 [#1] PREEMPT SMP
[    5.984673] Modules linked in: ipv6(+)
[    5.988408] CPU: 5 PID: 221 Comm: modprobe Not tainted 5.10.252-s5p6818 #1
[    6.005901] pc : ndisc_send_unsol_na+0x90/0x210 [ipv6]
[    6.106045]  ndisc_netdev_event+0x114/0x200 [ipv6]
[    6.110785]  call_netdevice_register_net_notifiers+0x134/0x170
[    6.116596]  register_netdevice_notifier+0xa4/0x1c0
[    6.121493]  ndisc_late_init+0x1c/0x28 [ipv6]
[    6.125832]  inet6_init+0x188/0x348 [ipv6]
[    6.174224] Kernel panic - not syncing: Oops: Fatal exception in interrupt
[    6.195838] Rebooting in 10 seconds..
```

链路：ipv6 是模块 → systemd 到 5.9s 才 `modprobe ipv6` → 此时 `eth0` 已经注册
→ `inet6_init` 注册 netdev notifier 时把 `NETDEV_*` 事件回放给已存在的设备
→ `ndisc_send_unsol_na()` 拿到未初始化的 `inet6_dev` → oops → panic。

改成 `CONFIG_IPV6=y`：`inet6_init` 属于开机早期 initcall，那时除 `lo` 之外没有
任何网卡，这条回放路径不成立；顺带省掉一次 modprobe。

## 为什么之前"以为挂死"

- run20（11-19 20:26 那版）能用，run21 之后不行。两者差异只有两处：
  config 里新加的 BPF/VXLAN/IPVLAN/GPIO_SYSFS 等 + 重写的 initramfs 脚本。
- 4.14 侧看起来"没反应"，其实每次都是 panic → `panic=10` → 自动重启回 4.14，
  全程只要 ~40s。当时用 easytier 判断"活着没有"，easytier 起得慢，就成了
  "挂死"的假象。**以后判断死活只用 LAN 的 ping + `uptime`，别用隧道。**

## 三板斧：没有串口怎么定位到"U-Boot 还是内核"

### 1) 用 U-Boot 自己打点（env 就是日志）

`boot_510` 里每一步都 `setenv ub N; saveenv`，Linux 起来后 `kb-envset show`
读回来：

| ub | 含义 |
|----|------|
| 1  | 开始加载内核 |
| 2  | 内核 ext4load 成功（25MB 的文件 U-Boot 能读） |
| 4  | 外部 initrd 也加载成功 |
| 3  | 即将 booti |
| 9  | booti 返回了 => 内核根本没被启动 |
| 停在 3 且没有 9 | booti 成功、控制权在内核 => 问题在内核侧 |

见 `boot/dbg-boot510.sh`。这是**区分 U-Boot 与内核责任分界**最便宜的办法。

### 2) 外部 initrd：不重编内核也能换 initramfs

`boot_510dbg` 槽从启动分区读 `kg-initrd.gz` 当 initrd（`booti addr initrd:size dtb`），
所以可以直接把某个内核里内嵌的 cpio.gz 抠出来换个内核试：

```
# 抠出内核里内嵌的 initramfs（gzip cpio）
python3 - <<'PY'
import zlib
d=open('Image','rb').read(); i=d.find(b'\x1f\x8b\x08')
o=zlib.decompressobj(16+zlib.MAX_WBITS); o.decompress(d[i:i+6000000],40000000)
open('kg-initrd.gz','wb').write(d[i:i+6000000-len(o.unused_data)])
PY
```

实测：把 run24 的 init 脚本挂到 run20 的内核上能正常启动 => 脚本没问题、
问题在内核，一次 1.5 分钟的测试就排掉了一个假设。

### 3) 二分：只改一个变量

对比两个内核镜像的 `Image` 头（`text_offset` / `image_size`）和内嵌 cpio 目录，
再用 `git compare` 缩小到具体文件。本次两次 compare 就把范围从"整个内核"
缩到"workflow 里新加的 9 个 config 行 + initramfs 脚本"。

## initramfs 日志为什么不写（已修）

旧脚本顺序错了：先按 `/dev/mmcblkXp1` 找启动分区，**之后**才 `mount devtmpfs`，
所以设备节点根本不存在，`LOG` 静默降级成 `/dev/null`，`510-boot.log` 从来没被
创建过。现在：先挂 devtmpfs/proc/sys，再找 p1（优先带 `/Image` 的那个，4.14 也
挂它，两边都能读），然后才开始记日志。

## 移动硬盘：脉冲不够，必须长期拉高（2026-11-20 修）

新内核起来后移动硬盘能枚举、`/mnt/usbdrive` 也挂上了，但 42 秒后
`usb 2-1: USB disconnect`，ext4 被打成只读，podman 报
`read-only file system`。

原因：HUB 的负载开关需要**一直**保持高电平。早先那版脚本用 libgpiod 打 1 秒
脉冲就释放（当时在 4.14 上观察"释放也保持导通"，其实是 sysfs 导出没释放的
假象）。线一释放，开关随之掉电。

现在的做法（`boot/usb-hub-power.sh`，已在板上）：

- `GPIO40 = gpiob8 = base 32 + 8`，走 sysfs（本版内核已开 `CONFIG_GPIO_SYSFS`）
- 导出 → `direction=out` → 低 2s → 高，**保持导出、永不释放**
- 已经存在 `/dev/sd*` 时只补电平，绝不断电
- 日志写 `/dev/kmsg`（`/var/log` 是 tmpfs，服务又早于 local-fs，写文件必丢）

冷启动实测：10.0s 断电 2s → 12.0s 拉高 → 13.9s 枚举成 `sda` → 自动挂载
`/mnt/usbdrive`（94G）。另外 fstab 的 `x-systemd.device-timeout` 提到 60s。
